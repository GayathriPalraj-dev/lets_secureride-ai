# Foundation architecture

## Boundaries and request flow

The client owns presentation and public configuration. The server owns HTTP policy and future private services. Contracts define only health response and API envelope types.

Browser → Vite development proxy → Express /api/v1 → health route → typed JSON envelope. The client checks incoming health data before displaying it. React Router supports a home page and a fallback page.

The contracts package exposes TypeScript source for type resolution. Consumers use import type, which is erased by compilation; no contracts runtime module is loaded. Its build emits declarations for review and future packaging. Each workspace is private.

## Server responsibilities

app.ts creates an app from validated configuration without listening. server.ts validates the current variables and owns the listener and bounded SIGINT/SIGTERM shutdown.

Request IDs are generated by the server, returned in the header and response, and used for logging. HTTP serializers omit URLs, headers, request bodies, and raw exceptions. Error responses expose only stable public codes/messages. Body limits, Helmet, CORS, compression, and an in-memory per-process API limiter form the initial middleware layer.

The health endpoint is liveness only. CORS controls browser access; it is not authentication. Proxy trust is disabled. Deployment must later define trusted proxy behaviour and assess a shared rate-limit store before scaling.

## Configuration and future AWS compatibility

Only current foundation variables are validated. Future secrets are neither needed nor consumed. Examples are documentation, not deployed credentials.

A future private S3/CloudFront frontend can serve the static client build. A future CloudFront API origin can route /api to Nginx/EC2 and the Express service managed by PM2. The current relative API URL supports that same-origin pattern.

Future Atlas, car-image S3, Secrets Manager/Parameter Store, CloudWatch, CloudTrail, Systems Manager Session Manager, and GitHub Actions OIDC integrations require separate plans and approval. No AWS resources, Nginx configuration, PM2 dependency, or active workflows exist in Step 2.

## Validation

Server tests cover health contracts, request IDs, 404s, safe internal errors, body limits, CORS, rate limits, and environment validation. Client tests cover the heading, loading, success, network/HTTP failure, and malformed responses with mocked network calls.
